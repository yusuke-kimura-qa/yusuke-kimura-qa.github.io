Case Study

MimicaQAの目で、AIと作ったPNGTuberアプリ

高解像度の立ち絵を、できるだけシンプルにOBS配信へ。 自分を最初のユーザーとして、Windows向けPNGTuberアプリを開発しています。

3行でいうと

  1. 実装はAI、何を作るか・出してよいかは自分が判断する分担で開発
  2. 自動チェックが全部通っても、Windows実機でのQAとリグレッションを終えるまでマージしない
  3. 実機で見つけたことは、直す・直さない・手順書に書くのどれかに決めて記録する
アプリ
立ち絵に口パク・まばたき・呼吸・表情切り替えを付けてOBSで使う
技術
C# / .NET 8 / WPF / NAudio、Windows 11 x64
状態
Free版のリリース準備中（BOOTHで配布予定）
ソース
非公開。面接などでは、実際の Issue → PR → QA の流れをお見せできます
なぜ作ったか 役割分担 進め方の変化 QAとしての判断 数字 いまの課題

なぜ作ったか

高解像度の立ち絵を用意できても、それを配信で動かすまでが大変です。 既存のPNGTuberアプリは、レイヤーの考え方を理解して自分で組み立てる必要があり、UIも英語。初心者には負担が大きいと感じていました。

Mimicaでは、Setupタブで「閉じた口」「開いた目」のように、手持ちの画像を上から順に1枚ずつ入れていけば完成する流れを目指しています。 これは自分自身の困りごとでもありました。

役割分担

AIに実装を任せるぶん、判断は手放さないようにしています。

自分

  • 課題と優先順位を決める
  • 製品方針・UX・Free/Supporterの範囲を決める
  • AIへの指示と、やらないことの線引き
  • Windows実機QA・リグレッション
  • PRの最終確認とマージ判断

AI

  • ChatGPT：課題・要件・QA観点を整理する壁打ち相手
  • Codex：初期の実装
  • Claude Code：移行後の実装・自動チェック

進め方の変化

最初から今の進め方だったわけではありません。 はじめは作りたいものをAIに伝えて、動いたら満足する、という作り方でした。

転機は、「既存アプリと同じものを作るなら、費用をかけてコピーを作っているのと変わらない」と気づいたことです。 Mimicaならではの価値を言葉にするために要件書を書き、そこから少しずつ進め方を整えていきました。

  1. 09-26
    検証記録を開始

    実機で確かめたことをTESTING.mdに残し始める

  2. 09-30
    UIを3タブに整理

    Live / Setup / Motion に分け、整列操作はFitだけに統一

  3. 10-01
    要件書を作成

    何を作り、何を作らないかを書き出す。Free版の範囲も文書化

  4. 10-01
    表情の切り替えをどのタブからでも

    範囲を既存のA/B/Cに絞って実装。実機QAでデグレなしを確認してからPR化

  5. 10-02
    Claude Codeへ移行

    使っていたツールが使えなくなったのを機に、開発ルールをCLAUDE.mdに明文化。人に引き継ぐときも文書がなければ目的が伝わらない、と考えたため

  6. 10-02
    Issue相談をテンプレート化

    目的・範囲・範囲外・受け入れ条件・QA観点・回帰リスクを、着手前に決める

いまの進め方

  1. 自分Issue相談目的・範囲・やらないこと・QA観点を決める
  2. AI実装短期ブランチで実装し、ビルドと自動チェックを通してPRを作る
  3. 自分実機QAWindows実機で確認し、結果をTESTING.mdに記録
  4. 自分マージQA結果を見て、mainに入れるかを判断

QAとしての判断

何に気づき、どう決めたかを、事象・判断・理由の順にまとめました。

探索テストで発見

リセットしたのに、構図がずれる

事象
実機での探索テスト中、設定をリセットすると、立ち絵が画像を入れた直後とは違う大きさ・位置に戻ることに気づいた。
判断
「リセット＝画像を入れた直後の見た目に戻る」のが自然。Fitボタンと同じ結果になるよう修正を依頼した。
確認
4000×8000pxの画像で、修正後の倍率と位置がFitと一致することを確かめた。

仕様判断 → 実機確認 → スコープ

名前に絵文字を使えるようにする

判断
表情セットの名前で、絵文字を許容する方針にした。文字数の数え方（結合絵文字・𠮷）、改行、空白だけの名前、IME変換中のEnterもQA観点に入れた。
事象
実機で境界値・改行・絵文字を実際に打鍵したところ、WPFでは絵文字が白黒で表示されると分かった。
判断
入力は許容し、カラー表示はスコープ外として記録に明記。
理由
崩れはなく、カラー化のために表示部品を作り直す手間と保守の負担に見合わないため。

実機の事実で手順を変える

OBSのおすすめ手順を書き換えた

事象
文書では「単色背景＋キー除去」をすすめていたが、実機では「透過背景＋ウィンドウキャプチャ（Windows 10方式）」の方が簡単で、髪や輪郭の見え方も問題なかった。
判断
要件書とREADMEのおすすめ手順を変更。背景方式を切り替えるとOBS側で再指定が必要なことも書き添えた。
理由
実際の利用環境で確かめた手順を、使う人への案内にするため。

やらないことを決める

困りごとがないなら、Issueにしない

事象
出力ウィンドウの最小化対策と、起動の高速化を検討した。
判断
出力ウィンドウは単体では最小化されないことを実機で確認し、Issue化をやめた。起動も体感1秒未満で困っていないため対象外にした。
理由
「できそうだから」ではなく、実際の動きと困りごとの有無で必要性を決めるため。

範囲を切り分ける

Free版とSupporter版の境界

判断
表情セットまわりの機能のうち、名前変更だけをFree版に切り出した。セットの追加・削除や4個目以降はSupporter版に回した。
反映
先に文書で範囲を確定させてから、名前変更を実装した。

数字

356 → 524

自動チェックの数。機能を足すたびに増やし、全部PASSをPRの前提にしている（実装はAI）

約1.5GB

3744×8841pxの実素材をOBSに取り込んだときのメモリ。30分経っても安定（自分のPCでの概測）

いまの課題

Setupタブに、入れた画像のプレビューがありません。どの画像がどこに入ったかをその場で確かめられないので、 まだ「本当に直感的」とは言えないと考えています。

  • 素材の欄に、入れた画像のサムネイルを表示する
  • 初心者に実際に使ってもらい、迷わず完成できるかを確かめる
  • 高解像度の画像を使ったときの、メモリの内訳を計測する

この開発から学んだこと

出来上がったアプリを探索テストするのも楽しい。

すべてが新鮮で、毎日学びがあり、充実しています。
